# External evidence for recalld retrieval evaluation and a memory-policy RL harness

Research date: 2026-11-13 (America/Los_Angeles). Primary papers, author repositories, source files, and publisher-maintained dataset cards were inspected directly. Repository links on `main` are mutable; a future execution manifest must pin commits and dataset hashes. This document reports research, not experiments or reproduced results. No personal recalld MCP calls were made.

## Recommendation and scope of evidence

Build trustworthy evaluation in this order: state-transition contracts; fixed-state retrieval diagnostics; conversational QA; chronological memory episodes; only then a narrowly scoped learned policy. LongMemEval is the most directly useful addition to the existing conversational evaluation. Small BEIR collections provide inexpensive retrieval diagnostics without an answer model. LoCoMo remains a regression dataset, with separate reporting for its scoring protocols and adversarial questions. Memory-R1 supplies a concrete policy/training reference, not evidence that RL will improve recalld.

**Evidence labels:** “Verified” means the linked primary source supports the statement, not that its experimental result was independently reproduced. “Local context” means repository documentation, not an implementation audit. “Proposal” and “analogy” describe engineering recommendations requiring local validation. No expected recalld accuracy, latency gain, or training return is estimated here.

## Local context and evaluation gaps

Read: [README](../../../../README.md), [architecture](../../../architecture.md), [benchmark methodology](../../../benchmark.md), [MCP documentation](../../../mcp.md), [guide](../../../guide.md), and the [research plan](../PLAN.md).

The architecture documents vector/FTS fusion, entity retrieval, graph expansion, temporal boosting, supersedes resolution, FSRS decay, and retrieval-induced forgetting. Direct recall and associative retrieval can strengthen memory; the query pipeline records access events asynchronously. Phase transitions discard content. Therefore an apparently read-only evaluation query can affect later episodes unless the harness deliberately freezes or restores state. This is a documented design implication, not a demonstrated race or corruption bug. See architecture §§4–8.

The benchmark documentation specifies fresh per-conversation instances, **decay disabled**, sequential LLM extraction, LLM query decomposition, and up to ten additional graph neighbors beyond the reported `top_k`. It also documents different invalid-`supersedes` handling between the benchmark's in-process path and public APIs. Production callers supply already-selected memories; the benchmark supplies its own extraction policy. Consequently:

- A QA score measures the combined extractor, search planner, retriever, context expansion, answer model, and judge. It cannot isolate the retrieval engine.
- `top_k` alone does not define equal answer-context cost; include neighbors, full text, graph annotations, and prompt overhead.
- With decay disabled, that benchmark does not validate forgetting schedules, irreversible content loss, or long-lived update behavior.
- A policy trained through the benchmark path can encounter different error transitions in production. Align the transition contract before collecting training trajectories.

These are scope limitations of documented methodology. This research neither validates nor disputes the README's headline scores.

## Primary-source findings

### LongMemEval: retrieval and answering must be measured separately

**Verified.** The official release contains 500 questions covering extraction, multi-session reasoning, updates, temporal reasoning, and abstention. It supplies S, M, and evidence-only oracle variants. The README announces cleaned histories in September 2025. The S history is roughly 115k Llama-3 tokens; M has roughly 500 sessions. Evidence annotations include `has_answer` and `answer_session_ids`; abstention is encoded by an `_abs` question-ID suffix. [Author repository and schema](https://github.com/xiaowu0162/LongMemEval#-dataset-format).

The paper explicitly evaluates recall and nDCG alongside QA. Its experiments distinguish indexing granularity, retrieval keys, time-aware retrieval, and reader behavior. Fact expansion of retrieval keys and time-aware retrieval help in the studied configurations; inaccurate inferred time ranges can remove needed evidence. These are configuration-specific findings, not universal gains. [ICLR 2025 paper, §§3.3 and 5; appendices E–F](https://arxiv.org/html/2410.10813v2).

The official QA scorer uses task-dependent judging rubrics: temporal answers have specified off-by-one tolerance, and knowledge-update answers may contain old information if the required updated answer is present. A custom stricter scorer therefore measures a different protocol. [Official `evaluate_qa.py`](https://raw.githubusercontent.com/xiaowu0162/LongMemEval/main/src/evaluation/evaluate_qa.py).

**Proposal.** Start with cleaned S and the matched oracle condition. Keep a frozen raw-round index as a baseline beside extracted memories. Preserve source-turn/session provenance for every derived memory. Measure whether evidence was retained, retrieved, and correctly used as three separate questions. Evaluate current-state and historical “as of” queries separately: replacing all old facts with their successors is not automatically correct for historical questions.

An oracle-evidence answer run is a diagnostic for reader errors, not a realizable retrieval system or a guaranteed mathematical upper bound. Keep its label-aware context assembly outside the normal ingestion and search path.

**Access/license.** The [official cleaned dataset card](https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned) labels the dataset MIT; the [repository license](https://github.com/xiaowu0162/LongMemEval/blob/main/LICENSE) is MIT. Use the named JSON files directly if the dataset viewer fails: the inspected card displayed an answer-type parsing error. Original versus cleaned histories, S/M/oracle, and custom regenerated histories are separate artifacts, not interchangeable train/test splits. The repository identifies ShareGPT/UltraChat filler sources; custom corpus regeneration requires preserving upstream provenance and checking those assets' terms rather than assuming the repository license settles every input's rights.

**Current extension.** The authors now publish [LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2), with 451 curated questions over multimodal web-agent trajectories, web and enterprise domains, and accuracy/latency evaluation. Its abilities include dynamic state tracking, workflow knowledge, and environment-specific mistakes. This is a distinct benchmark, not the cleaned V1 release. The repository is marked Apache-2.0; dataset-specific terms and full data access were not verified here. Defer it until the text adapter is stable and trajectory/multimodal coverage can be stated honestly; do not label a text-only transformation an official V2 result.

### LoCoMo: useful regression coverage, limited independent histories

**Verified.** The current author release contains ten conversations, with session timestamps, dialogue IDs, QA/evidence annotations, generated observations and session summaries, and annotated event summaries. It is a selected subset of an earlier 50-conversation release. Images themselves are not distributed; URLs and captions are supplied. [Official release description](https://github.com/snap-research/locomo); [ACL 2024 paper](https://aclanthology.org/2024.acl-long.747/).

The released evaluator uses token F1 for categories 2/3/4, sub-answer F1 for category 1, and phrase matching for category-5 abstention. When context/evidence conditions are absent, its retrieval-recall output falls back to `1`; blindly averaging that field can therefore imply retrieval success without evidence. [Official evaluator, `eval_question_answering`](https://raw.githubusercontent.com/snap-research/locomo/main/task_eval/evaluation.py).

**Proposal.** Preserve both the upstream scoring track and recalld's existing binary-judge track, with explicit names. Report categories 1–4, category 5, and all categories separately, including counts. Never compare binary judge accuracy directly to token F1 or a result excluding adversarial questions. Missing evidence should be “unscored,” with a coverage count, in a new diagnostic metric; retain upstream behavior only in a clearly labeled compatibility result.

Use conversation-grouped development/evaluation partitions. Ten histories do not provide 1,986 independent user environments, even though the local benchmark reports 1,986 questions. Report per-conversation results and paired uncertainty grouped by conversation; uncertainty estimates with only ten groups remain fragile. Existing prompt iteration on this public benchmark makes it a regression track, not a pristine holdout.

**Access/license.** The [author license](https://raw.githubusercontent.com/snap-research/locomo/main/LICENSE.txt) is **CC BY-NC 4.0**. Treat commercial use or training-data redistribution as unresolved until the intended use is checked against those terms or separately authorized. Public availability is not an unrestricted commercial grant. Caption-only evaluation must be declared; dereferencing image URLs introduces availability and third-party rights issues. Do not silently use annotated event summaries as ordinary dialogue input.

### MemoryBank and MemGPT: useful architectural analogies

**Verified, MemoryBank.** MemoryBank uses retrieval, ongoing updates, and an Ebbinghaus-inspired forgetting/reinforcement mechanism. Its evaluation includes simulated dialogue and qualitative user dialogue in an AI-companion setting. [Author paper](https://arxiv.org/abs/2305.10250). The [official repository](https://github.com/zhongwanjun/MemoryBank-SiliconFriend) describes 100 manually written probing questions over simulated histories; its [software license is MIT](https://raw.githubusercontent.com/zhongwanjun/MemoryBank-SiliconFriend/main/LICENSE). The scope of separate model/checkpoint and underlying dialogue-data rights should be checked before reuse.

**Analogy, not evidence for recalld.** MemoryBank motivates testing retention against utility and elapsed time. It does not establish recalld's FSRS thresholds, ACT-R parameters, retrieval-induced suppression, or permastore cutoff. Human-memory terminology is not a substitute for measuring task utility. Compare no forgetting, a simple age/budget rule, and current decay under matched storage and answer-context budgets before tuning a more elaborate mechanism.

**Verified, MemGPT.** MemGPT manages limited main context and external storage through model-issued functions and interrupts. Its context queue can be summarized/evicted while the underlying messages remain in recall storage. The paper evaluates conversational and document-analysis tasks. [Paper, §2 and §3](https://arxiv.org/html/2310.08560). The implementation project is now [Letta](https://github.com/letta-ai/letta), whose inspected [current software license is Apache-2.0](https://raw.githubusercontent.com/letta-ai/letta/main/LICENSE). A current Letta checkout is not automatically the 2023 experimental implementation; pin the historical implementation and separately resolve evaluation-data/model terms for reproduction.

**Analogy, not equivalence.** Context eviction and irreversible memory deletion are different transitions. Test whether useful data survives outside the answer context, whether retrieval can recover it, and whether summaries preserve provenance. A page-in/page-out mechanism cannot justify destructive phase transitions merely because both reduce active context size.

### Memory-R1: a concrete learned-operation reference with important release distinctions

**Verified paper claims.** Memory-R1 uses a Memory Manager with ADD/UPDATE/DELETE/NOOP and an Answer Agent that distills retrieved memories. It studies PPO and GRPO, uses exact-match downstream answer reward, freezes the answerer while training the manager, and fixes the manager while training the answerer. The paper reports learning with 152 QA pairs and evaluates LoCoMo, MSC, and LongMemEval. These are author-reported results, not reproduced evidence about recalld. ArXiv v5 appendix B.2 says 24 preceding turns, while Algorithm 1 says 50; that preparation detail is internally inconsistent. [Paper v5, §§3–4 and appendices B/E](https://arxiv.org/html/2508.19828v5); [ACL 2026 publication record](https://aclanthology.org/2026.acl-long.583/).

**Verified release status.** The current [official README](https://raw.githubusercontent.com/yansikuan/memory-r1/main/README.md) documents data preparation, separate manager/answer-agent training trees, and evaluation components. An indexed older README said code was forthcoming; that search result is stale. The current repository has an [Apache-2.0 software license](https://raw.githubusercontent.com/yansikuan/memory-r1/main/LICENSE). Its README and arXiv v5 present different headline relative gains; do not mix their numbers into a single comparison.

The [data README](https://raw.githubusercontent.com/yansikuan/memory-r1/main/data/README.md) identifies a 1,307-QA test artifact, bundled parquet/Qdrant training assets, noncommercial restrictions on LoCoMo derivatives, and live model/embedding calls needed to regenerate data. It warns that regenerated row UUIDs, Qdrant collections, and parquet must be produced together. The [split implementation](https://raw.githubusercontent.com/yansikuan/memory-r1/main/data/scripts/build_dataset.py) removes category 5 and implements `118` as first conversation train, second validation, remaining eight test; `811` is an alternative. This is not recalld's all-ten/all-category protocol.

The [manager documentation](https://raw.githubusercontent.com/yansikuan/memory-r1/main/memory_manager/README.md) identifies a verl fork with a `memrl` layer, GPU training, and external answer/judge configuration. Availability of source and launchers does not establish that artifacts reproduce a particular paper version; neither training nor checkpoint availability was tested here.

**Proposal.** Borrow the separation between operation policy and answering policy. Initially freeze the answerer, retriever, embedding model, and extraction format; compare scripted and prompted operation policies on identical state snapshots. Exact match is attractive for narrowly structured answers, but can penalize correct paraphrases; validate it against adjudicated cases before treating it as a reward. Do not train on LoCoMo-derived assets for unrestricted product use merely because the training code is Apache-2.0.

### BEIR and hybrid ranking: establish retrieval controls before learning a policy

**Verified.** The original BEIR paper evaluates 18 datasets and ten retrieval systems across heterogeneous tasks. BM25 is a strong baseline in its experiments; reranking and late interaction perform well on average with additional computation. This is evidence for broad evaluation and explicit cost measurement, not a claim that a 2021 method dominates current encoders or recalld. [NeurIPS 2021 paper](https://arxiv.org/abs/2104.08663).

The [official toolkit](https://github.com/beir-cellar/beir) supplies corpus/query/qrels interfaces and nDCG, MAP, recall, precision, and MRR evaluation. Its dataset table distinguishes downloadable collections from BioASQ, Signal-1M, TREC-NEWS and other collections requiring separate acquisition. Software is Apache-2.0; datasets have separate terms. [Official dataset table](https://github.com/beir-cellar/beir#beers-available-datasets).

**Proposal.** Start with full SciFact and NFCorpus corpora, small enough to make repeated retrieval evaluation practical; they test retrieval plumbing, not conversational memory or lifecycle management. Their BEIR cards list approximately 5.18k and 3.63k corpus rows respectively, both labeled CC BY-SA 4.0. Preserve source attribution and dataset-specific notices; do not substitute the toolkit license. [BEIR SciFact card](https://huggingface.co/datasets/BeIR/scifact), [BEIR NFCorpus card](https://huggingface.co/datasets/BeIR/nfcorpus). Use native development labels for tuning where available and keep evaluation labels out of fitting. Treat unjudged documents according to the benchmark metric, without claiming they are proven irrelevant.

**Verified fusion evidence.** Reciprocal Rank Fusion sums `1 / (c + rank)` across ranked lists; the original paper fixed `c = 60` after a pilot and evaluated TREC/LETOR combinations. [Cormack, Clarke and Büttcher, SIGIR 2009, equation 1](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf). Bruch, Gai and Ingber find parameter sensitivity in RRF and favorable results for a tuned convex combination in their studied in-domain and out-of-domain settings. [Fusion analysis, arXiv v2 / TOIS](https://arxiv.org/abs/2210.11934v2). Neither source establishes a universal winning fusion rule.

**Proposal.** Compare lexical-only, vector-only, current fusion, RRF, and a development-tuned normalized score mixture. For RRF, define absent-list contribution as zero, stable tie handling, candidate depths, and duplicate-ID merging. A starting `c = 60` is a baseline, not a proven optimum. For a convex mixture, record normalization and select its weight on development data only. First hold candidate pools constant to isolate ranking; then separately measure candidate-generation changes.

The local architecture's FTS-only cap and path-dependent graph/entity scoring make candidate coverage and score comparability worth measuring. They are hypotheses to test, not evidence that the current formula is defective. Add graph expansion and reranking only after the simple controls; compare equal total context tokens and report their additional latency.

## Leakage controls and scoring contract

Everything in this section is a **proposed harness requirement**.

1. **Separate actor input from labels.** Ingest only dialogue, speaker roles, source IDs and permitted timestamps. Strip `has_answer`, `answer_session_ids`, QA answers, evidence annotations, category labels, and annotated event summaries before extraction/indexing. Keep these in an evaluator-only sidecar. Query-time actors receive the question and allowed query date, not gold labels. Training rewards may consult training labels; actor prompts must not receive future evaluation questions or answers.
2. **Preserve causal time.** Distinguish event time, source-message time, ingestion time and evaluation clock. In chronological episodes, expose only history available at the query cutoff. Never translate a historical event date into elapsed storage age implicitly. An “as of” query must not resolve to a future successor.
3. **Group before deriving data.** Split original conversations/users before extracting memories, creating summaries, constructing reward examples, or caching embeddings. Keep aliases, repeated facts and near-duplicate histories together. S/M/oracle views of the same LongMemEval question are not independent holdouts. Varying distractors around shared evidence does not create an independent test example.
4. **Prevent evaluation from teaching the system.** Use a fresh clone of the same post-ingestion snapshot per fixed-state question, or a verified side-effect-free evaluation adapter. Do not write generated answers, judge feedback, retrieved snippets or gold rationales back into that snapshot. Chronological evaluation intentionally retains effects, but has a fixed declared order and a separate score track.
5. **Keep retrieval labels honest.** Source-ID overlap is evidence-location coverage, not proof an extracted summary retained the relevant proposition. Audit a sample for content preservation. Deduplicate mapped source evidence; do not credit one memory multiple times. Missing annotations are unknown, not failures or automatic successes. Report annotated-denominator coverage.
6. **Freeze the decision boundary.** Record dataset revisions/hashes, split IDs, prompts, extraction outputs, model revisions, embedding configuration, tokenization/chunking, candidate limits, graph settings, clock, seeds, scorer version, and parse/retry policies. Cache model outputs by full configuration hash to support exact replay, but measure live latency separately.
7. **Audit the judge.** Save per-example outputs, raw judgments and failures. Separate model refusal, transport failure, parse failure, and wrong answer. Calibrate on a manually reviewed, category-stratified sample, including stale-but-plausible answers, partial multi-hop answers, correct paraphrases, and answer text that tries to instruct the judge. Use blinded adjudication for disputes. Record judge agreement rather than assuming a different model family eliminates bias.
8. **Protect the holdout from iteration.** Select fusion weights, prompts, retrieval depth, reward weights, and checkpoints on development data only. Disclose prior public-benchmark exposure and possible base-model contamination; lack of access to pretraining corpora prevents proving its absence. Add newly authored, rights-cleared synthetic histories for fresh regression coverage, without presenting them as equivalent to natural user data.

## Prioritized pragmatic evaluation plan

These are proposed future stages; none was executed for this document. Do not begin with an exhaustive model/grid search.

| Priority | Smallest useful deliverable | Measurements and decision gate |
|---|---|---|
| P0: deterministic state contract | Isolated temporary stores, controlled clock, snapshot/reset, validated action schema, observable completion of pending effects | Replaying identical recorded inputs yields identical canonical logical state; invalid actions have declared effects; API and training adapter agree. Gate all policy training here. |
| P1: retrieval diagnostics | Raw-round/provenance baseline on cleaned LongMemEval S; full small BEIR corpora; lexical, vector, current fusion and RRF | Candidate evidence coverage, Recall@5/10/20, nDCG@10, MRR where first-hit relevance is meaningful; missing-label coverage; latency and index size. Confirm metric adapters before tuning fusion. |
| P2: end-to-end regression | Frozen answer model, matched context-token budget; LongMemEval S plus oracle; LoCoMo upstream and custom-judge tracks | QA by ability/category/conversation, answerability and abstention errors, evidence-supported answers, input/output tokens and failures. Diagnose lost-at-extraction versus missed-at-search versus reader failure. |
| P3: chronological lifecycle | Rights-cleared synthetic episodes with corrections, redundant facts, explicit forgetting, distractors and time advances | Stale-answer rate, update correctness, retained useful evidence versus storage budget, forbidden/deleted content returned, cross-namespace exposure, and episode QA. Compare no decay, simple budget/age rule, current lifecycle. |
| P4: policy feasibility | Fixed retriever/answerer, same episode snapshots, scripted policies versus a prompted operation policy | Action validity, future QA utility, cost, destructive errors, repeated-action behavior and reward audit. Train only if a controllable policy failure remains after correctness fixes. |
| P5: constrained RL pilot | Rights-cleared grouped train/dev/test data, one learned policy, frozen environment version | Multiple training seeds, untouched held-out histories, paired policy comparisons, cost/utility frontier, and explicit hard constraint checks. Expand to M/V2 only when justified by measured failure modes. |

For the first development pass, a small stratified LongMemEval subset can validate adapters and costs. Label it development-only and record selection before seeing outputs. Freeze the protocol before a full reported run; never infer full-benchmark performance from that subset. BEIR can run without a generative answerer; reserve paid QA calls for comparisons that resolve a specific diagnostic question.

Define retrieval metrics at a consistent unit (turn, round, session, document). Add **all-required-evidence coverage** for multi-hop questions; ordinary recall can hide a single missing essential fact. Report abstention precision and recall, plus accuracy on answerable questions so “always abstain” cannot look useful. Report both micro averages and group/category breakdowns. For A/B comparisons, preserve paired question outputs and group resampling by conversation or shared history; publish intervals and effect sizes without treating clustered questions as independent samples.

Report p50/p95 query latency with sample count and environment, cold versus warm state, index-build/extraction costs, total answer-context tokens, storage bytes, memory count and errors. A larger retrieved context or a slower external reranker is not a free retrieval improvement. Keep fixed-state and chronological scores separate.

## Why training must wait for reliable state transitions

This is an engineering inference from recalld's documented mutability and the outcome-based policy formulation, not a claim experimentally established by an external paper.

An RL harness needs a defined transition from `(state, action, elapsed time)` to `(next state, observation, reward, termination)`. If an action silently disappears, updates one index but not another, completes after the reward is measured, or behaves differently through the production API, the reward cannot be attributed cleanly to the policy. The learner may optimize a harness artifact. Fixing the engine later changes the environment the policy learned.

Stochastic transitions are compatible with RL; unexplained or unreplayable state changes are the problem. Model sampling may remain stochastic, provided inputs, outputs and randomness are recorded and branches start from equivalent snapshots. Determinism is a debugging/replay requirement, not a claim that real conversations are deterministic.

### Minimum environment contract before collecting training rollouts

- **State:** memory content and provenance, phases, strength/stability and timestamps, supersedes/other edges, namespace, index membership, deletion state, pending events, and a controlled clock. Include caches when they affect observable behavior; normalize irrelevant generated IDs for logical-state comparisons while retaining their trace mapping.
- **Actions:** initially STORE, STORE_WITH_SUPERSEDES and NOOP; add REINFORCE and FORGET only after their semantics are independently verified. Do not pretend Memory-R1's UPDATE is identical to recalld's versioning operation. Validate ownership, target existence, namespace, payload and allowed transition before execution.
- **Transition boundary:** each action returns a declared outcome and reaches an observable completion barrier before scoring. Snapshot/reset must include derived indexes and pending work, not just metadata. Duplicate delivery and retry behavior must be explicit. Do not assume reinforcement is idempotent.
- **Observations:** expose only permitted current evidence and tool outcomes to the policy. Keep privileged full-state inspection and reward labels in the evaluator. A partially observable policy can still run against a fully logged environment.
- **Reward:** evaluate future query utility under a fixed answerer, with explicit costs for storage, tokens and calls. Keep deletion/privacy/namespace constraints as hard gates rather than small penalties that answer gains can outweigh. Validate the reward on adversarial and paraphrase cases before choosing weights on development data.
- **Counterfactual branches:** apply alternative actions to independent clones of the same state, with the same simulated time and future query stream. Do not compare successive actions on a shared evolving store and call the difference a policy effect.

Required transition fixtures should cover successful store/retrieve; malformed and cross-namespace references; duplicate requests; supersession chains and historical queries; reinforcement with clock advancement; each phase boundary; forget followed by query/graph traversal/restart; and restoration/replay. Separately check interruption/recovery if it is part of the intended production contract. A test must specify whether tombstone relay is allowed and whether deleted content is ever visible; graph-node survival alone is not the same as content resurrection.

Before RL, compare store-all, deterministic duplicate handling, and the current prompted memory policy under matched budgets. If a supervised/rule-based correction resolves the measured problem, no policy training is required. If RL remains warranted, train one component at a time, version the environment and rewards, and rerun held-out evaluation after any engine change. External memory-policy results motivate this investigation; only reliable local transitions and independent utility measurements can justify deploying a trained policy.
