# Shared specification contracts

Integration revision 1, 2026-11-13. These are agreed implementation contracts for A1–A6, not implemented behavior. They supersede draft alternatives in the six specifications. [INTEGRATION-REVIEW.md](INTEGRATION-REVIEW.md) records decisions, implementation order and outstanding empirical release gates. No new research, production change or training is authorized here.

## Ownership and version names

| Owner | Authoritative boundary |
| --- | --- |
| A1 storage/recovery | Canonical encoding, transactions, operation/batch receipts, lineage/generations, removal ledger, snapshots, migration and readiness publication |
| A2 retrieval | Eligibility, candidate budgets, version resolution, graph/RIF ranking, coverage and rank provenance |
| A3 lifecycle | Timestamp meaning, injected clock, pure projection/feedback, policy revisions and irreversible phase transitions; A1 persists these |
| A4 tools/namespaces | Wire names/schemas, namespace resolution, embedding profile identity/validation, transport compatibility and pagination |
| A5 performance | Instrumentation, workload manifests, latency/resource gates and optimization evidence |
| A6 evaluation | Isolated replay, frozen manifests/splits, source-evidence mappings, trace schema and statistical evaluation |

Versions are independent; an API upgrade never migrates a namespace's lifecycle policy implicitly.

| Name | Initial integrated value and selection |
| --- | --- |
| `contractVersion` | Integer 1 when omitted; opt-in 2 via MCP argument or HTTP `Recalld-Contract-Version`; retain v1 for at least two releases |
| `retrievalSemanticsVersion` | Integer 1 under contract v1; integer 2 under contract v2; not a second independently selectable public switch |
| `rankingProfile` | `baseline-v1` formula weights in both; semantics, lifecycle version and `rifMode` separately identify behavior |
| `lifecycleVersion` | `legacy_access_v1` for migrated **and new** namespaces; `explicit_feedback_v2` only by explicit namespace migration |
| `rifMode` | Contract v1 preserves configured legacy query-local behavior, reported as `legacy` or `off`; contract v2 defaults `off`; operator/harness-only `shadow` and `experimental` use A2's capped algorithm |
| Canonical versions | A1 owns `canonicalSchemaVersion=2`, `recordSchemaVersion=2`, `backupFormatVersion=2`, `exportFormatVersion=1`, `receiptVersion=1`, `requestHashVersion=1`; these do not imply API or lifecycle v2 |
| Harness versions | A6 owns `manifestVersion=1`, `traceSchemaVersion=1`, `sourceMappingVersion=1`; every manifest pins the other versions plus derived-index formats |

On disk/internal Rust may use snake_case; wire fields use camelCase. Receipt result encoding is named `receiptVersion`, not `contractVersion`. Namespace `policyRevision` and per-record `recordGeneration` are decimal-string counters; the latter is a last-mutation concurrency token, distinct from the store-wide generation. Unknown required versions fail closed. Derived formats may rebuild; canonical formats require an explicit migration.

## Generations, receipts and batches

All externally compared generations carry lineage: `GenerationRef = {storeId: UUID, generation: decimal-string}`. Canonical decimal encoding is `0` or a nonzero digit followed by digits, no sign/leading zeros; supported range is 0–9223372036854775807. Never use a JSON number or compare generations across lineages. `readGeneration` and barrier targets are GenerationRefs. A receipt uses `{storeId, operationId, committedGeneration: "42", receiptVersion: 1, outcome, replayed}`. Mutation preconditions use `storeId` plus optional `expectedGeneration: "41"`; this is a **store-wide** compare-and-swap. A3's internal record/policy checks are separate.

`idempotencyKey` requires an explicit `storeId` from discovery, including in legacy requests that opt into keyed writes. Explicit stale store IDs fail `conflict/STORE_LINEAGE_MISMATCH` before replay or mutation. Unkeyed legacy calls may omit lineage; they have no retry guarantee. Receipt lookup uses store ID, namespace ID (even if deleted) and operation ID. Matching replay is checked before the expected-generation test.

Keys are scoped to `(storeId, namespaceId, key)` **across operation kinds and transports**. A different operation with the same key conflicts. Namespace creation and batch manifests use the distinguished catalog scope, not a mutable name masquerading as a namespace ID; normalized creation target is part of the payload. Other namespace operations use stable, never-reused namespace IDs. Replay lookup can use an explicit namespace ID after purge; an ambiguous name-only retry fails rather than binding to a newly created namespace.

Retain receipts, request hashes, batch manifests and removal-ledger entries for the lifetime of the lineage, including after namespace deletion. No seven-day TTL, `idempotencyExpiresAt`, or silent old-key reuse. Hash version 1 uses SHA-256 over a length-delimited canonical request encoding: operation kind, contract version, resolved immutable scope, expected generation, normalized fields/expanded defaults, ordered arrays, and supplied embedding bytes/profile. Exclude generated IDs/times and external provider output. Persist IDs/status/counts/numeric outcomes and hashes, never copies of removed text/embeddings; client resubmission supplies batch payloads for resumption. Hashes are not forensic erasure. A4 normalizes; A1 computes/persists identity and generated results.

Batches commit per item in input order; no atomic-batch claim. A keyed batch reserves a durable catalog manifest with ordered per-item hashes, stable child operation IDs, and outcomes. Manifest bookkeeping advances canonical generation but confers no atomicity on items. Outer validation fails before reservation; invalid items become indexed failures without blocking later valid items. Each successful child outcome is committed with its mutation. A crash between rejection and recording its failure can repeat validation but cannot repeat a committed mutation. Resume with the same full payload and key; committed outcomes and finalized failures replay unchanged. `notAttempted` and `unknown` remain pending; reconcile an uncertain commit by child operation ID before resuming. A new key is required to retry a finalized failure.

Outcomes contain every input index, with `status=ok|error|notAttempted|unknown`, resolved scope when known, and receipt or structured error. Counts obey `total=succeeded+failed+unresolved`: committed `ok` items count as succeeded, final errors as failed, and pending/unknown as unresolved. No top-level committed generation; return `batchOperationId` and item receipts. All ready successes: HTTP 200; mixed outcomes or committed-but-not-ready items: 207; all final failures: 422; zero successes with unresolved work: 503. Non-ok aggregate outcomes set MCP `isError=true`. A committed item remains committed even when readiness fails; expose its receipt and `ready=false`, never relabel it safely retryable as a new write.

Receipts replay historical numerical/ID outcomes without mutation. They cannot recreate deleted content. Access-recording query receipts record only exposure outcomes, never old result payloads; a replay may recompute a read-only result at the current generation with a separate readGeneration, without recording exposure again. Revalidate content visibility before returning any data. This is exactly-once mutation, not a promise of an identical query response after later writes.

## Namespace, embeddings and observation

Resolve store/search/list scope once: explicit namespace, otherwise frozen connection/server default, otherwise `default`. By-ID get/reinforce/forget/single-similarity resolves the record's namespace; an explicit namespace is an assertion (`conflict/NAMESPACE_MISMATCH`). A3 must use this same rule. Unknown UUID is not found; terminal-identity and receipt lookup can retain scope after content deletion. Namespaces organize data, not authentication. Memory namespace is immutable; moving content means a new UUID.

Ordinary queries are single namespace. The existing explicit cross-namespace similarity operation alone can opt into `namespaceScope=allCompatible` in v2 (legacy `sameNamespace=false`); list searched/excluded namespaces and preserve per-result namespace. Supersedes and new graph edge writes require both endpoints in the same namespace. A1 checks endpoint existence and, for Supersedes, cycles/branches atomically using A2 semantics; invalid new edges conflict. Legacy foreign edges never authorize cross-namespace traversal. A1 may remove incident edges across scopes as integrity cleanup.

`embeddingDim` accepts integers 1–8192, then requires equality with the namespace and single active profile. Same dimension with a different model/preprocessing/normalization identity is incompatible. A4 defines profile identity, A1 persists it, A5 uses it in caches, A6 freezes it in manifests. Unknown legacy provenance stays unknown until explicit attestation or re-embedding; metadata reads/export remain available. Dimension boundary parser tests are not proof that an arbitrary active provider supports those dimensions.

Search, direct fetch and batch fetch default `recordAccess=true` under both API and lifecycle versions. Lists/stats/admin inspection remain non-observing. True mode records one exposure per distinct returned UUID, synchronously, with an A1 receipt; zero results cause no write. Batch fetch across namespaces uses ordered per-namespace exposure mutations/receipts and partial outcomes; repeated UUIDs share the first exposure outcome, never a second event. A single mutation cannot cross namespace scope. The response distinguishes the pre-exposure readGeneration from the committed receipt generation. V1 lifecycle updates the decay anchor; v2 lifecycle records exposure only. Explicit feedback alone changes stability. Query-local RIF never persists in either contract.

`recordAccess=false` forbids canonical/receipt/history/graph/lifecycle writes and attributable deferred work. Caches/telemetry may not alter later eligibility/ranks/retention. Tool hints reflect the most mutating permitted call; get/fetch/recall cannot be labeled read-only while true is their default. A6 always passes false, disables autonomous sweeps and freezes/bypasses behavioral caches.

One A3 clock sample and policy revision are pinned per operation. `legacy_access_v1` uses canonical materialized strength for both hard minimum-strength eligibility and ranking; a current projection is diagnostic only. `explicit_feedback_v2` uses pure current-clock projection consistently for eligibility and ranking. API/retrieval v2 does not itself switch strength sources. Derived cached values cannot override either source. RIF operates after hard eligibility and cannot retroactively change it. A clock advance invalidates v2 projection caches even without a generation change; keys include generation, clock and policy revision.

## Retrieval, deletion and readiness

Contract v2 uses strict `versionMode=current` by default. Return only proven current eligible terminals; an unusable known successor omits the predecessor with aggregate diagnostics. `history` returns independently eligible retained versions without score inheritance, never erased text or an as-of reconstruction. Public `asOf` is unsupported. A6 uses a chronological snapshot to exclude evidence not yet ingested. Both modes reject tombstones; neither ghosts nor tombstones relay associative activation. Content-free tombstone identities may be traversed solely to resolve a Supersedes chain, with namespace checks and no ineligible IDs in diagnostics; they are never seeds/results or sources of inherited scores. Hard delete removes incident edges; current status is relative to retained structural evidence, not knowledge of lost history. New cycle/branch writes are rejected; legacy ambiguity is reported unresolved.

A2's budget profile `retrieval-v2-default` is authoritative: `B=min(1600,max(100,8*L))` for vector/FTS/metadata; entity admits at most `2*L`; FTS examines at most 12,800 distinct rows; graph depth 0–3 with 400 expanded states and 12,800 examined edges; supersession at most 64 edges per origin and 12,800 edge examinations per query. Graph retention is bounded by distinct admitted seeds plus examined edges; no additional hidden 3,200-union/1,600-node cap. Vector/entity/metadata scans have no hidden early scan limit. Apply hard filters before candidate allowances in every channel and replacement. Supersession inheritance is the same `max(own, inherited)` for existing and injected replacements. Deterministic ties use UUID bytes.

Coverage always distinguishes candidate limiting, source exhaustion, work exhaustion, degraded channels and final result limiting. A filled result page is not exhaustive retrieval. A5's alternative budgets are named experimental arms only. Default response has no new 64/256 KiB truncation cap; those are measured experiments, not public defaults. If an existing transport limit cannot fit the response, return explicit `RESPONSE_TOO_LARGE`, never silently drop IDs/content. A6's 4,096-token evidence cap is separate from A5's 2,048/8,192-token stress arms.

A1 owns a generation-consistent read view and derived-view watermarks. Successful ready writes synchronously publish required views. A committed write whose publication fails returns `unavailable/INDEX_NOT_READY`, `commitState=committed`, its receipt and readiness; it has not rolled back. Point reads may use canonical records/payloads after pending canonical effects complete. An affected search channel blocks/rebuilds or reports unavailable; no invented canonical FTS scorer is required. A2 canonical eligibility scans operate inside a coherent read view, not as a fallback for unavailable search semantics. Independent ready channels may return explicitly degraded partial coverage at that same generation; all requested channels unavailable means request failure. No stale-index empty success.

Shared readiness shape is `{storeId, committedGeneration, ready, pendingWork, derived:[{name, appliedGeneration, ready}]}` with decimal-string generations and integer work counts. `barrier(GenerationRef, deadline)` rejects foreign lineage, completes accepted work through that target including transitive tasks, and returns readiness; A6's default deadline is 30 monotonic seconds. A snapshot additionally stops admission and requires zero pending work and all captured views consistent with its generation. A1 implements publication/barrier state; A3 registers lifecycle work; A6 consumes it.

Forget, hard delete and destructive phase loss commit A1's payload-free removal ledger. Retained-state restore captures the target ledger under ownership, verifies ancestry, merges all available compatible removal state and applies it before serving; unreadable ledger/unknown ancestry fails closed. Restore creates a new storeId, records snapshot/ledger provenance, and rejects old-lineage retries. Migration and lossless reverse export preserve lineage/receipts/ledger. Imported old receipts remain historical, not keys newly reusable under the new lineage.

An older backup cannot reveal later deletions if every newer copy is lost. Explicit historical restore is fresh-destination-only, historical/read-only and excluded from ordinary serving; it reports deletion coverage through the snapshot or supplied ledger and unknown later coverage. Separate explicit promotion without a complete later ledger acknowledges possible reappearance of later-deleted content. It is data-loss recovery, never ordinary rollback or a no-resurrection guarantee. No operation erases old archives forensically.

A6 reset is an isolated fixture clone, not production restore: stop workers, create a fresh inaccessible root, restore exact clock/config/RNG, canonical receipts/ledger and pinned versions, then rebuild and barrier/hash-check before actions. It may preserve the fixture lineage for deterministic replay only because clones never share a production endpoint or external retry domain. Production restore always changes lineage. Pending executor queues are not serialized. Frozen-state runs verify unchanged records, receipts, graph, ledger and lifecycle after false-mode reads.

## Evidence, provenance and performance gates

A1 owns persisted embedding/lifecycle/lineage provenance; A4 defines its public representation. A2 owns channel/score/graph/inheritance explanations for returned UUIDs. A6 owns dataset-turn-to-memory mappings and evaluator-only labels in sidecars; A1 preserves canonical IDs and any stored mapping references during export, without adding a second source-label store. A5 emits timings/counters into A6's versioned traces. No owner may infer missing model revisions, feedback dates or source support.

Evidence remains: 487 baseline Rust passes; seven added tests with three passes/four failures; actual supersession **stage** reproduction 0.9/rank 1 versus 0.1/rank 11. The d384/10k exact-index p95 is 232.835 µs in one run, excluding the full pipeline. Python ablations and SQLite toy transactions are models, not engine correctness/performance results. See the [baseline REPORT](../experiments/baseline/REPORT.md) and [ablation REPORT](../experiments/ablations/REPORT.md).

| Change class | Required gate (none is an achieved result) |
| --- | --- |
| Instrumentation alone | At most 5% p95 latency and throughput regression |
| Performance-only optimization | At least 10% targeted full-pipeline improvement with paired 95% interval excluding zero; other p95/throughput/RSS regressions at most 5% |
| Correctness/API/lifecycle rollout | No speedup required; at most 10% p95 overhead against a pinned comparable fixture/provider baseline, plus absolute workload budget. Required correctness cannot be waived for speed; a failed gate pauses promotion, not reintroduces the bug |
| Mixed correction plus optimization | Establish corrected baseline first, then apply the 5% collateral/10% improvement gate to the optimization separately; do not stack allowances |
| Backend replacement | A1's explicit parity/recovery and 1.20 latency / 1.25 resource-duration / 0.80 throughput ratio gates; separate migration class, not an exemption for unrelated optimizations |
| RIF/ranking or lifecycle default change | A2/A3 paired quality gates plus at most 10% p95 regression; their different utility tests remain separate |

A5 freezes target hardware, workload, absolute p95/RSS/error budgets before candidate measurement; baseline characterization supplies feasible values without claiming a production SLO from kernel timings. Missing measurements/budgets block performance promotion, not containment. A6 owns grouped intervals/sample plans. Insufficient samples or missing strata are a failed-to-establish gate, never a positive result. Exact search stays default; backend choice, ANN, lifecycle promotion and learning remain conditional on their stated empirical gates.
