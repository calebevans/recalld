# A1 — Storage correctness, recovery, and canonical transactions

Status: implementation proposal, 2026-11-13. Owner: A1. Nothing below is a claim of implemented behavior or completed validation. This action item changes storage and recovery, not retrieval policy. It follows [CONTRACTS.md](CONTRACTS.md) and [PLAN.md](../PLAN.md). Integrated under shared contract revision 1; no implementation or new experiments were performed.

## 1. Outcome and evidence

Ship incremental containment on the current backend first. Then compare a single SQLite canonical database against a single redb canonical database behind the same storage interface. SQLite is the preferred hypothesis, not a selected replacement. Keep the repaired current engine until fidelity, crash recovery, and measured workload gates pass. Do not couple this work to ANN or embedding-provider expansion.

The baseline identified by the research plan is `5aa4692c7d326d2ef10712939eb01484a520e891`. Source symbols below were inspected in the current workspace; implementation must record its actual revision. The following are source-supported risks, not failures reproduced by this author:

| Problem | Evidence and consequence |
| --- | --- |
| Compaction commit is not atomic with its recovery decision | `RedbStorageEngine::compact_text_log` commits offsets through `MetadataStore::batch_update_records`, then writes `.compaction-meta-committed`. `recover_text_compaction` discards `.new` when that marker is absent. A crash in between can select the wrong payload file. Writing the marker first merely reverses the unsafe window. |
| Tombstones retain obsolete vector slots | API deletion tombstones and frees under one outer write lock, but storage `delete_memory` frees the recorded slot unconditionally. `VectorStore::free_slot` lacks owner validation. Hard deletion after reuse can affect another memory. External reachability of this sequence is unproven. |
| Restore accepts an incomplete file inventory | `extract_backup` verifies only listed CRCs. Missing namespace vectors can be recreated by normal engine opening. Manifest version compatibility and checksum validity do not establish completeness. |
| Restore lacks target ownership | `restore_from_backup` stops the default daemon opportunistically, then renames the target without acquiring its engine lock. An embedded writer or `--no-stop-daemon` process may retain the old directory. |
| Namespace identity has two inputs | `insert_memory(namespace_id, record, ...)` allocates through the argument while metadata indexes `record.namespace_id`. Neither equality nor reconciliation is enforced there. |
| Phase publication can reorder | `update_decay_state` commits first, then separately locks/transitions the phase bitmap. Shared-reference callers can publish transitions in a different order. Insert/delete/batch/rebuild/persist paths also need one serialization rule. |

## 2. Invariants and proposed interface

1. A committed generation selects exactly one canonical state. UUIDs and namespace IDs remain stable. Generations are monotonically increasing counters in the shared supported range 0–9223372036854775807 within a store lineage; exhaustion is an error, never wraparound. Use `(store_id, generation)` externally, with generation encoded as a decimal string to avoid JSON number precision loss.
2. Every mutation resolves exactly one namespace before touching storage. A memory's namespace is immutable. A4 owns resolution and user-visible validation; A1 validates again at the storage boundary. An edge write belongs to its source namespace and requires a same-namespace target. Reject new cross-namespace, cyclic or branching Supersedes mutations atomically under A2 semantics; incoming integrity cleanup is not cross-namespace retrieval.
3. Text/vector bytes referenced by committed metadata must already be durable or part of the same database transaction. Reclamation follows loss of ownership, never precedes it. Tombstone, hard delete, supersession, and decay remain different operations.
4. Every acknowledged write returns a durable operation receipt. An immediate read observes that generation or a later consistent generation. A stale index must not silently omit the write. A query pins one read view, including graph and filters, for its duration.
5. Missing canonical files or invalid ownership fail closed. Rebuild only derived artifacts. No open-existing or restore validation path may initialize absent canonical files.

Proposed internal interfaces (names are normative intent; adapt Rust types to existing conventions):

```text
MutationContext { store_id?, resolved_namespace_id, idempotency_key?, expected_generation? }
WriteReceipt { store_id, operation_id, committed_generation, receipt_version, outcome, replayed }
apply(ctx, Mutation) -> WriteReceipt
lookup_operation(namespace_id, operation_id) -> receipt | not_found
read_view(min_generation_ref?) -> ReadView { store_id, generation, ... }
barrier(generation_ref, deadline) -> Readiness { store_id, committed_generation, ready, pending_work, derived }
validate_existing(path, mode = StrictReadOnly) -> ValidationReport
backup(snapshot_options) -> BackupManifestV2
restore(archive, target, options) -> RestoreReport
```

`store_id` is required for keyed writes and expected-generation conditions; stale lineage conflicts. External generation fields use decimal strings and GenerationRefs as defined in CONTRACTS. `expected_generation` is an optional store-wide compare-and-swap, checked inside the transaction; a mismatch returns conflict without mutation. `Mutation` includes insert, content update, lifecycle patch, tombstone, hard delete, explicit edge changes, and namespace configuration changes. A3 supplies lifecycle fields/semantics. Namespace creation reserves a never-reused ID within its transaction; deletion operates on that resolved ID. Multi-namespace administrative work is decomposed into explicit per-namespace operations with receipts. Incoming edge cleanup is an integrity consequence of deleting a record, not implicit permission to query other namespaces.

A4 maps storage errors to invalid input, not found, conflict, unavailable, and per-item batch outcomes while preserving legacy text decoding. Add internal causes `CorruptStore`, `OwnershipMismatch`, `UnsupportedFormat`, `IndexNotReady`, and `CommitOutcomeUnknown`. Never report a post-commit indexing failure as an ordinary rolled-back write. Resolve an uncertain database commit by reopening and checking the durable operation ID; never free its payload based solely on a returned I/O error.

### Receipts and retry scope

Scope explicit keys to `(store_id, namespace_id, idempotency_key)` across mutation types. Allocate operation UUID before commit. Use requestHashVersion 1 (SHA-256) over the shared length-delimited canonical encoding of operation type, contract version, resolved namespace, expected generation, normalized request fields/expanded defaults, and caller-supplied embedding bytes/profile. Do not include server-generated timestamps/UUIDs or external embedding-provider output in the request hash. Persist the generated result and actual embedding provenance separately. Repeated matching requests return the original UUIDs, outcome, and generation without reinforcement, timestamps, or new writes; mismatches conflict. Check a matching existing receipt before applying the expected-generation condition again. A4 must resolve the same namespace on retry; omission may resolve differently after a configuration change.

Default retention: keep key/hash/result receipts for the lifetime of the store lineage, including namespace deletion (IDs are never reused). This provides retry safety without an undisclosed expiry. Receipts contain IDs, operation kind, counts, and status, not deleted text or embeddings. Hashes are not forensic erasure. Receipt growth is measured by A5; finite retention requires a separately versioned A4 contract, not opportunistic cleanup. Operations without explicit keys still receive receipts, but blind resubmission is not deduplicated. Backup and migration retain receipts. Restoring an older snapshot explicitly loses receipts and writes newer than that snapshot; assign a new restore lineage ID and report its source lineage/generation. Old-lineage requests must conflict, not silently be retried against the restored state. Preserved older receipts remain historical under their origin lineage; restoration does not rebind their keys to the new lineage. Catalog-scoped creation/batch receipts, pending manifests and namespace-ID replay after deletion follow CONTRACTS. No expiry field is emitted.

Batch default remains per-item commits and receipts, in input order, with partial outcomes. Persist the catalog manifest and stable child operation IDs defined in CONTRACTS; finalize each successful child outcome with its mutation. Preserve indexed finalized failures, distinguish pending/notAttempted and unknown outcomes, and reconcile uncertain commits before resumption. Manifest bookkeeping advances generation but never implies batch atomicity. A4 serializes succeeded/failed/unresolved counts and item receipts. A single item that changes a record and its explicit edges is one logical mutation. Chunked namespace purge is a resumable administrative operation with a namespace `deleting` state; reject new writes there and report progress until complete. No success receipt for the whole purge before its final chunk commits.

## 3. Stage I: containment on the existing engine

Land independently reviewable repairs before enabling the complete receipt interface. Existing adapters retain existing response shapes during the first repairs; do not advertise the new atomic mutation contract until all write paths participate. Disable automatic compaction until the generation protocol passes its tests. On startup with ambiguous legacy compaction markers, preserve both files and fail with a recovery diagnostic. CRC-valid text alone cannot identify which offsets were committed; do not guess or delete `.new`.

### 3.1 Transactional compaction selection

Add a versioned control table in `meta.db` containing `store_id`, `schema_version`, `committed_generation`, and `active_text_generation`. A text-generation descriptor contains a never-reused generation UUID, safe relative filename, format version, and a sealed prefix length/SHA-256 recorded when compacted. New text files have a header containing their generation UUID. The sealed prefix remains unchanged; later appends are validated by entry checksums and bounds. New installations and upgraded clean stores start with a registered initial generation.

Replace marker-driven renaming with generation-named files (`fulltext.<uuid>.dat`) selected by metadata. Under the exclusive engine mutation gate, with old readers drained:

1. Read all retained text references and the active descriptor at generation G. Preserve all reachable text, not merely phase-Full records. Write a new file with its generation header and relocated entries. Verify lengths/checksums; sync the file, then its parent directory. No metadata changes yet.
2. In **one redb write transaction**, check G, update every relocated offset, insert the new descriptor, switch `active_text_generation`, advance committed generation, and record the compaction receipt. Empty-text compaction still commits the selection transaction. Do not call a helper that separately commits offsets.
3. After commit, switch the in-process text handle while the gate remains held. A publication error makes the engine unavailable until recovery; it must not serve old bytes under new offsets. A filesystem marker has no authority in this protocol.
4. After no reader/snapshot can reference the previous file, unlink it and sync the directory. Cleanup failures are reported and retried; they do not invalidate the committed generation.

Startup opens metadata first without serving reads, selects its descriptor, and validates the selected file/header/sealed prefix and every referenced extent before use. An unselected new file is an orphan; a selected missing file is corruption. A crash before step 2 selects the old generation; a crash after it selects the new one. No rename of payload files is required at the commit boundary. Orphan cleanup runs only after successful validation and never deletes the selected file.

For a clean legacy store, copy its `fulltext.dat` to a generation file, validate and sync it, then register that descriptor in the format-upgrade transaction. Preserve original offsets by reserving the same header size or rewriting offsets in that transaction; choose rewriting if the new header does not fit. Retain the original file until upgrade validation completes. Ambiguous interrupted legacy compaction requires an intact backup or independent evidence sufficient to reconstruct every record; normal startup must not infer safety from marker order. Old binaries cannot open the upgraded layout safely: require a format gate and documented downgrade procedure.

### 3.2 Slot ownership and payload allocation

Add canonical `vector_owners[(namespace_id, slot)] = {memory_id, allocation_epoch, embedding_hash}` in `meta.db`. Add optional vector reference to record schema v2: `None` for tombstones; otherwise `(slot, allocation_epoch)`. Keep old record decoding for conversion. The owner table, record, tag/namespace indexes, generation, and receipt change in the same transaction. Do not infer ownership from phase alone.

Replace public raw `free_vector_slot(ns, slot)` with an engine-owned reclamation path carrying expected memory ID and allocation epoch. `VectorStore` cannot decide ownership by itself; the engine validates canonical ownership under its mutation gate. A stale release token must return ownership mismatch without touching bytes or the free list. A repeated already-completed release is an idempotent no-op. Hard deletion of a tombstone has no vector release to perform.

Allocation initially uses an in-memory free set rebuilt from canonical owners and file capacity on startup; the existing on-disk free list is a cache, never authority. Reserve a free slot, write its embedding, sync bytes and any capacity/header changes, then commit ownership and metadata. On failure before a definite commit the reservation can be reclaimed; ambiguous commit requires recovery first. Updating an embedding uses a different slot (copy-on-write), never overwrites a live slot before commit. After tombstone/delete commits owner removal, clear/free its old slot before admitting another allocator. A crash between commit and cleanup leaves unowned bytes, which recovery can reclaim safely. Free-list cycles, duplicate owners, and owned slots marked free are validation failures or trigger rebuilding from owners, never allocation from suspect pointers.

Initial conversion derives ownership from non-tombstoned records, checks one live owner per `(namespace, slot)`, dimensions, slot bounds, and decodable vectors. Tombstone slots are ignored. Duplicate live owners or missing payloads block upgrade with affected IDs. Historical vector corruption cannot always be detected from metadata; do not claim conversion repairs it. Record hashes from conversion protect subsequent changes, not historical correctness.

### 3.3 Namespace insertion and phase serialization

Before any payload allocation, reject mismatched `id` versus `record.id`, mismatched namespace argument versus `record.namespace_id`, nonexistent/deleting namespace, incompatible dimensions/profile, and duplicate UUID. New `InsertMemory` accepts one namespace identity; construct the disk record inside storage. The legacy signature remains a checking shim during conversion. Namespace IDs are not reused, and new namespace directories/files are synced before metadata publishes their existence. Failed publication leaves quarantinable unreferenced files. Startup opens referenced namespaces strictly, never `open_or_create`.

Introduce a `MetadataStore` publication `RwLock`, independent of the existing bitmap lock. All record/index mutations take its write side **before starting the redb write transaction**, and hold it through phase publication. Phase scans and combined metadata/index snapshots take its read side before their read transaction. Lock order: engine mutation gate → metadata publication gate → database transaction → phase bitmap. No path may acquire these in reverse; internal helpers accept a held guard rather than reacquire it. Apply this rule to insert, decay, access patches that affect phase, tombstone, hard delete, batch update/tombstone, namespace purge, rebuild, and checkpoint serialization. Direct metadata callers receive the same protection, not merely API adapters with an outer lock.

Publish actual committed phase and owned slot from the transaction result; do not assume every inserted/imported record is Full. Tombstones are excluded from slot bitmaps; count them from records. Store a serialized checkpoint envelope `{format_version, applied_generation, payload_length, checksum, bitmaps}` under the same publication gate. The checkpoint transaction does not increment logical generation. Load a checkpoint only if its generation matches canonical state and its decoder validates lengths, duplicate namespaces, slot ownership, trailing bytes, and format version. Otherwise rebuild from canonical records before exposing phase queries. Unknown future canonical formats fail; unknown derived-index formats rebuild. On an in-process publication failure invalidate the bitmap and rebuild under the gate or fail queries; no successful response with a stale bitmap. Incremental checkpoint frequency is an A5 optimization, not a correctness condition.

### 3.4 Remaining multi-file transactions and derived views

The first fixes do not magically make `edges.db`, FTS, and metadata one transaction. Before exposing `apply` with receipts, add a durable mutation-effects table in `meta.db`: operation/generation plus deterministic edge puts/deletes, affected peer counts, and derived-index invalidations. Commit these intended effects with the record mutation and receipt. Apply edge effects idempotently (absolute values, not counter increments), sync `edges.db`, then record completion. All edge writers use this route. A pending mutation blocks new engine reads/writes until its effects replay; startup replays before ordinary orphan-edge cleanup. This deliberately simple containment barrier avoids readers seeing half a record/edge operation. The record commit is the logical commit; replay failure returns unavailable with the operation ID and committed generation, not a claim of rollback. Receipts never say aborted after commit.

After replay, synchronously publish FTS, entity, cache, graph, exact-vector, and phase views at the committed generation before acknowledging ready success. Maintain `applied_generation` per derived view. Readers hold the publication gate for a consistent view. On rebuild failure fail the affected query with `IndexNotReady`; point reads can use canonical metadata/payloads at a consistent generation. Do not serve an older search index as a successful current search. Stage I defaults to blocking until rebuild rather than inventing a new FTS scoring fallback. CONTRACTS fixes the readiness shape: A1 publishes per-view watermarks and pending work; A4 serializes it and A2 reports unavailable channels. Independent ready channels may return explicitly degraded results at the same pinned generation; all requested sources unavailable means failure. A5 measures blocking costs. A2 may canonically scan eligibility, but this does not supply missing FTS semantics. Cache keys include store lineage and generation; restoring a prior generation cannot reuse stale cached values.

This replay protocol is containment debt, to be removed by a winning canonical backend. If measured costs block rollout, keep containment and the atomic-receipt API gated until its guarantees exist; consolidation still requires the stated fidelity/recovery/workload gates. Auto-link suggestions may be separate explicit operations; never silently include them in a receipt whose transaction cannot persist them.

## 4. Backup and restore

### Ownership and crash-safe replacement

Use a stable sibling lock outside the replaceable data directory: `<canonical-parent>/.<basename>.recalld-owner.lock`. Resolve the target identity from the canonical parent and final basename; reject symlink targets and aliasing arrangements that cannot provide one lock identity. Never unlink this lock. Engine open, offline backup, restore, and migration all acquire it first and hold it for their full ownership interval. Retain the existing internal `recalld.lock` as a compatibility check, with fixed lock order sibling → internal → engine gate. The first deployment requires all old processes stopped/upgraded: a legacy binary that ignores the sibling lock cannot be made safe during rename by advisory locking alone. Unsupported concurrent old-binary starts are an explicit rollout constraint.

`--no-stop-daemon` skips the shutdown request only; it never bypasses ownership. `--force` skips confirmation only. Backup must no longer continue after failed locks. Busy ownership produces unavailable and leaves the target untouched. Daemon stop is targeted to the selected data directory and is not proof of ownership.

Restore validates into a fresh sibling staging directory on the same filesystem, never extracts over the target. Acquire ownership before inspecting/replacing the target and hold it through validation, publication, and final reopen. Use a fsynced sibling restore journal recording operation ID, old/staging paths, expected store IDs, archive hash, and states `Prepared`, `OldMoved`, `NewInstalled`, `Complete`. Sync each populated file/directory and parent after journal/rename changes. Publish by renaming old target to a unique retained directory, then staging to target. This pair is **not** called an atomic exchange. Engine startup under the same lock resolves the journal before opening: if the old target moved but staging remains, finish the validated install; if target already matches the expected new store, finish validation/mark complete; if staging is unavailable before install, restore the old directory. Unexpected identities or multiple ambiguous targets fail closed with both copies preserved. Fault recovery inspects paths/IDs as well as journal state, since a rename can precede the next journal fsync.

### Deletion retention and historical restoration (A3 handoff)

Persist `removal_ledger[(origin_lineage, namespace_id, memory_uuid)] = {terminal_kind?, removed_fields_mask, operation_id, generation}` in the same canonical transaction as irreversible content removal. `terminal_kind` distinguishes tombstone from hard delete; the mask records full-text, summary/tag, and embedding removal under A3 semantics. Merge masks by union and terminal state monotonically (hard delete dominates tombstone). Retain ledger entries for the lineage lifetime, including namespace purge, independently of record existence and receipts. Entries contain no removed payload. Reject reusing terminal UUIDs; matching old receipts are historical outcomes and never recreate records. Stage I stores this table in `meta.db`; both candidates include it in their canonical schema, manifest and lossless export.

Restore has two explicit modes:

- **Retained-state recovery (default for an existing target):** while holding target ownership, export its ledger and verify lineage ancestry before replacing anything. Merge the archive ledger with all available newer retained deletion/removal state into staging. Apply terminal identities and removal masks to restored records, vectors, incident edges as required by A3, and every derived index before any serving. Commit this reconciliation as a new generation in the new restore lineage; record source snapshot generation and ledger provenance separately. Retain the captured ledger durably with the restore journal so interruption cannot lose it. Historical receipts must not bypass these constraints. If the target ledger is unreadable or ancestry cannot be established, ordinary retained-state restore fails; it must not downgrade automatically to historical mode.
- **Isolated historical restore (explicit option, fresh destination only):** restore precisely the available snapshot plus any supplied compatible ledger, use a new lineage, and mark the result historical/read-only. It is excluded from normal daemon registration and recall. Its report states `deletion_coverage=through_snapshot` or the supplied ledger's known coverage, with later deletion state unknown. A separate explicit administrative promotion is required to serve it; without a complete newer ledger that promotion acknowledges possible reappearance of content deleted after the snapshot. It is data-loss recovery, not an anti-resurrection guarantee or normal rollback.

If all copies of newer deletion state have been lost, no restore algorithm can infer those deleted identities from an older backup. Do not promise otherwise. Backups retain the ledger only as of their snapshot; operators needing later deletion coverage must retain a newer store/ledger backup. Retained-state recovery guarantees suppression for the merged available ledger, not undiscovered deletions or removal of bytes from historical archives. A3's rollback and no-resurrection tests apply to retained-state recovery; historical inspection and explicit promotion must carry the stated limits. A3 and A6 use these same coverage limits; isolated fixture reset is the explicit nonproduction exception in CONTRACTS.

### Complete manifest and validation

`BackupManifestV2` uses backupFormatVersion 2 and canonicalSchemaVersion 2 and includes backend, store/source lineage, snapshot generation, namespace IDs/names/profiles/dimensions, required canonical file inventory, each file's exact length and SHA-256, selected text generation where applicable, logical record/tombstone/vector/edge/receipt counts, configuration schema, and a derived-artifact inventory. Checksums detect damage, not archive authenticity. V1 CRC archives remain importable only after the same complete semantic validation; do not silently fill missing files.

For the current backend require `meta.db`, `edges.db`, the metadata-selected text file (legacy `fulltext.dat` for clean v1), and every referenced namespace's vector file, including valid empty-store headers. Derive this requirement from validated metadata, then compare with the manifest; an empty manifest cannot declare an empty database. Require pending-effect tables/receipts/control tables in upgraded formats. Exclude lock files and obsolete compaction files. FTS/cache/phase checkpoints are derived and can be omitted if explicitly rebuilt. Configuration sufficient to interpret persisted namespaces, embedding profiles and versioned lifecycle policy is exported without credentials; target provider credentials remain external. Provider calls are never required to validate or restore existing vectors.

Reject missing/duplicate/extra undeclared archive entries, duplicate normalized paths, traversal, absolute paths, links, special files, inconsistent sizes, unsupported versions, and expansion beyond declared sizes. Check space for staging plus retained old store before publication; extraction still handles disk-full safely. Validate read-only without create/repair: database integrity, record decode, UUID uniqueness, namespace references, text extent/checksum validity, vector dimensions/ownership/hashes, edge endpoints/types, and counts. Dangling graph edges are reported as corruption in the snapshot, not silently cleaned during validation. Rebuild derived indexes only after canonical validation, in staging. Run offline point reads and deterministic exact-search fixtures before publication. A restore result states the snapshot generation and whether it deliberately replaced newer state.

Stage I backup default is quiescent: acquire ownership, finish recovery/replay, flush all canonical stores, capture one generation, copy while writes remain prohibited, validate, then publish the archive by synced rename. Do not package a hot SQLite file without its consistent snapshot protocol. In the SQLite candidate use its backup API to a standalone staging database under a pinned application snapshot; validate its generation and contents. For redb default to a quiescent synced copy until the pinned version's supported snapshot/export API is verified. Backup duration is measured; no claim of online equivalence precedes validation.

No automatic deletion of backup archives or retained pre-restore directories in this work. They may contain forgotten content. List them and require explicit retention cleanup; deleting live records is logical removal, not forensic erasure of backups, WAL, free pages, or filesystem copies.

## 5. Stage II: canonical-store spike

Implement both candidates only after containment acceptance; this specification does not authorize running the spike now. Use the same `apply`, receipt, snapshot, validation, and export interfaces. Persist all canonical records, text, embeddings, namespaces, lifecycle configuration, explicit edges, receipts, and generation in **one database transaction domain**. Slots/text offsets cease to be canonical in either candidate. Exact vector indexes remain rebuildable derived data keyed by UUID, namespace/profile and generation.

### Logical schema shared by both candidates

| Relation/key | Required fields and constraints |
| --- | --- |
| `store_control` singleton | Schema/format version, lineage UUID, committed generation, lifecycle policy version, namespace counter; restore ancestry separate from active lineage. |
| `namespaces` by stable ID | Name and A4-normalized unique name, immutable dimensions/profile identity, decay configuration, state, created time. Preserve display name and existing case-insensitive behavior. |
| `memories` by UUID | Namespace FK, record schema version, summary, optional full text, phase, strength/decay strength/stability/difficulty, permastore, created time, all A3 lifecycle timestamps and bounded history, revision generation. Preserve legacy `last_accessed_at` during versioned A3 conversion; do not invent missing observation timestamps. |
| `memory_tags` | Memory UUID, canonical tag, ordinal where needed to preserve structured tag ordering and original representation. Namespace/tag indexes are derived. |
| `embeddings` by memory UUID | Namespace/profile, dimension, little-endian f32 bytes, byte hash; validate length equals dimension × 4 and numeric validity. Tombstones have no embedding or content. Legacy unknown model provenance is explicitly unknown, not labeled with the currently configured model. |
| `edges` by `(source, type, target)` | Existing direction/type, weight bits, auto-created flag, created time, revision; both endpoints exist. Tombstones may remain endpoints according to A2; hard delete removes incident edges transactionally. Outgoing count is derived/recomputed or updated in the same transaction. |
| `operations` and unique key index | Namespace/catalog scope, operation UUID, optional key, request hash/version, generation, receiptVersion 1/outcome; no deleted payload copies. Namespace identity retained after purge. |
| `batch_manifests` | Catalog-scoped key/hash, ordered child hashes/operation IDs and committed/final/pending outcomes; lifetime retention and resume semantics from CONTRACTS. |
| `removal_ledger` | Origin lineage, namespace ID, UUID, terminal kind and irreversible removed-field mask, operation/generation; retained independently of record/namespace deletion. |

Preserve serialized f32 bits for lifecycle and edge values in export; SQL REAL conversion must not introduce drift. Use the shared checked generation range 0 through signed 64-bit maximum; wire generation values are decimal strings, never JSON numbers. Reject overflow. Canonical validation is common code, not weaker in the redb implementation. Unknown required record fields block migration; optional extensions are versioned and preserved.

SQLite default: one database, WAL, `synchronous=FULL`, foreign keys enabled on every connection, one writer queue, bounded busy timeout (5 seconds → unavailable), local filesystem. FTS5 lives in that same database with explicitly transactional update/delete logic and a rebuild command; keep existing tokenizer/scoring configuration for parity. Store exact vector bytes as BLOBs, without requiring a vector extension. Measure checkpoint cost/WAL growth and verify backup while writes occur. Do not attach separate canonical databases or relax durability to win a benchmark.

redb default: one database with typed tables for the same relations, synchronous durable commits using the supported API of the pinned version, one writer queue, and explicit transactional constraint checks. Put full text and vector bytes in that database, not external canonical files. FTS remains an external derived SQLite index with a generation watermark and readiness barrier. Verify the pinned redb durability/snapshot APIs during implementation; the evidence note did not establish latest upstream behavior for redb 2.6.3. Keep dependency versions fixed across comparison unless a separately documented compatibility upgrade is required.

### Measurement and decision gates

A5 owns instrumentation; A6 owns isolated fixtures/provenance. Compare repaired current storage, consolidated redb, and SQLite with identical durability, dimensions, input corpus, exact retrieval, and semantic operations. Default synthetic sizes: 1k, 10k, 100k records; dimensions 384 and 1536; one and 16 namespaces; text-size buckets 256 B, 4 KiB, 64 KiB; sparse and dense graph cases; single writer and mixed 1-writer/8-reader workloads. Include single and batched ingestion, lifecycle updates, delete/reinsert churn, filtered exact/FTS queries, cold open/index rebuild, backup/restore, and disk-full/recovery. A resource cap may omit a cell only with a recorded limitation; it cannot support a production default for that unmeasured range.

Record revision, toolchain, hardware/filesystem, durability options, seeds, warm/cold protocol, at least five independent runs per cell, samples, p50/p95/p99 latency, throughput, writer wait, peak RSS, steady/peak disk and WAL size, restart/rebuild time, and backup/restore time. Compare confidence intervals and raw distributions. Embedding network time is excluded and reported separately; neither Python timing nor an in-memory surrogate is engine throughput.

Gate defaults, proposed thresholds rather than results:

- Zero canonical fidelity differences, missing acknowledged operations, namespace violations, ownership failures, or crash-recovery invariant failures. All tests in section 7 pass on supported local filesystems.
- Exact-search IDs and deterministic tie-breaking match the common oracle; vector scores within absolute `1e-6`. FTS parity uses the same configuration/version, identical ordered IDs and absolute score tolerance 1e-6; a mismatch blocks migration rather than leaving tolerance selection to an implementation agent.
- Against repaired current storage, the upper 95% confidence bound on the candidate/baseline ratio is at most 1.20 for p95 read/write latency and at most 1.25 for peak RSS, steady disk, cold readiness, backup and restore duration in required cells. Lower confidence bound for throughput ratio is at least 0.80. If measurements are too noisy, gate remains open; gather more samples under A5's protocol. Report p99 and peak temporary disk even where no ratio gate is set, and require enough staging space before deployment.
- Among candidates passing all gates, choose SQLite by default for the simpler canonical/FTS commit boundary. Select redb instead only if it passes all gates and SQLite fails, or a recorded A5 workload shows a material benefit (at least 20% p95 improvement with nonoverlapping confidence intervals on a declared critical workload) without another gate regression. If neither passes, keep containment; do not force replacement.

Thresholds are frozen for the comparison; any revision requires a new versioned protocol before new candidate measurements. There is no measured speed claim here.

## 6. Migration, compatibility, rollout, and rollback

1. Deploy containment behind a versioned storage-format capability check. First release may leave compaction disabled while its protocol is validated. Take a complete quiescent backup before format upgrades. Require old binaries/processes retired before sibling-lock and generation-layout activation; new formats are not writable by old engines.
2. Gate canonical backend selection on section 5. Keep existing backend default until a candidate passes; no production dual writes. Read-only shadow comparisons use synthetic fixtures or an explicitly authorized snapshot, never personal data in research fixtures.
3. Acquire stable ownership, quiesce source, complete pending effects, and export a backend-neutral versioned stream plus manifest. Preserve IDs, names, tags, all timestamps/history and float bits, phase, tombstones, exact text/vector bytes, embedding provenance, every edge type/attribute, policy configuration, operation receipts and generation. Physical slots/offsets and secondary caches are not fidelity requirements. An export is a new artifact, not a rewrite of the source.
4. Import into a fresh sibling destination in bounded transactions while marked `importing`; it is never queryable until a final validation transaction marks it ready at the source generation. Resume by export ID and checksummed chunk sequence, not duplicate insertion guesses. Rebuild indexes and compare counts by namespace/phase/type plus sorted per-record, embedding, edge, receipt, and configuration hashes. Full logical hashes, not sampled reads alone, establish fidelity. Verify representative query parity through A2/A6 fixtures.
5. Use the restore journal/ownership protocol to publish the validated destination. Preserve lineage and generation during forward migration (unlike restore to an older snapshot), and report backend/schema version. Keep service read-only through startup and smoke checks. Enable writes only after the gate passes, retain the old store and export, and record cutover generation.
6. Before new writes, rollback swaps back under ownership after verifying both copies remained unchanged. After new writes, reopening the stale old store is forbidden. Default rollback is offline full export of the current canonical state into a **fresh** destination supported by the rollback binary, including deletes, removal ledger, receipts, namespaces, lifecycle state, and edges; validate and publish using the same gates. Reverse-import capability is a cutover prerequisite. If newer schema semantics cannot be represented, remain on the new backend in maintenance mode and fix forward; restoring an older snapshot is explicit data-loss recovery, not lossless rollback.

A3 schema changes require versioned readers/writers and a coordinated reverse-export policy. No backend migration may reinterpret decay behavior or overwrite unknown provenance to satisfy validation. Retained old stores/backups require explicit cleanup, including their forgotten content.

## 7. Acceptance tests (future implementation work)

Use isolated temporary stores with synthetic deterministic vectors, injected clocks, and no provider/network calls. A6 records provenance and results. Add subprocess failpoints and deterministic concurrency scheduling; unit tests that merely mirror function bodies are insufficient. Kill-at-boundary tests validate process interruption, not arbitrary hardware power-loss; add I/O fault injection and supported-filesystem crash testing before claiming broader durability.

| Test | Required observable result |
| --- | --- |
| Compaction crash matrix | Put dead text before two live entries so offsets change. Interrupt before/after new-file sync, directory sync, transaction commit, handle publication, and unlink. Reopen repeatedly: each UUID has exactly original text; selected descriptor matches offsets. Include empty compaction, repeated compaction, rename-independent cleanup errors, and commit-outcome uncertainty. Missing selected file fails, unselected file never wins. |
| Legacy ambiguity | Construct both old/new files with valid CRCs at plausible offsets and missing committed marker. Upgrade preserves both and fails diagnostically rather than guessing. Clean legacy upgrade round-trips every text extent. |
| Slot reuse | Insert A, tombstone A, insert B reusing its slot, hard-delete A. B's exact vector/hash/search result survives and slot is never double-allocated. Repeat delete/release, stale epoch, wrong namespace, crash after owner removal, crash after payload sync before commit, embedding copy-on-write, free-list cycle and duplicate-owner cases. |
| Namespace rejection | Mismatched argument/record namespaces and IDs fail before file size, free-set, receipt, or generation changes. Equal-dimension foreign namespaces still fail. Missing/deleting namespaces and wrong profile/dimensions fail. |
| Phase schedule | Pause writer 1 after commit before bitmap publication, start writer 2 and a phase reader. They cannot observe/reorder an intermediate bitmap. Cover Full→Summary→Ghost, tombstone/reuse, import in non-Full phase, purge, and serialization/checkpoint concurrent with updates. Compare every phase scan with canonical records/owners before and after reopen. |
| Checkpoint decoding | Stale generation, truncated lengths, corrupt checksum, future derived format, duplicate namespace, wrong slot owner and trailing bytes rebuild or error without returning a silently incomplete scan. |
| Receipt atomicity | Crash after durable commit before response; same key returns identical result/generation after reopen. Different payload conflicts; different namespace has independent key scope. Concurrent identical keys commit once. Failed prevalidation leaves no receipt. Restore lineage mismatch is explicit. |
| Effects and visibility | Crash between metadata commit, edge application, completion mark and each index update. Startup replays once logically; no doubled edge counts. Immediate point/exact/FTS/entity/graph reads see committed content or explicit unavailable, never false successful omission. `recordAccess=false` leaves canonical generation and lifecycle bytes unchanged. |
| Backup completeness | Remove each core or namespace file from both archive and manifest; include an empty manifest and zero-length vector file. Restore fails before touching target. Verify all namespace payloads, tombstones, profiles, edge attributes, receipt hashes and policy configuration, not only aggregate counts. |
| Restore ownership/recovery | Hold engine open in another process, with and without `--no-stop-daemon`/`--force`: restore cannot replace it. Kill at every journal/rename/fsync boundary and restart twice; exactly one selected complete store, old copy retained, no newly initialized missing store. Test nondefault target and rejected symlink alias. |
| Deletion-aware restore | Back up A, then forget/hard-delete A and degrade B. Restore with the retained ledger: A never serves, B retains its removal mask, and an old receipt cannot recreate either payload. Interrupt ledger capture/merge/publication and recover safely. With all newer state deliberately absent, historical restore is isolated and reports unknown later coverage; normal retained-state restore does not claim protection. |
| Archive/error handling | Bad SHA/CRC/size, duplicate paths/entries, traversal/links, unknown schema, disk full, permission and fsync failure preserve the original usable target and report cause. No output success until semantic validation and final reopen. |
| Backend round trip | Export/import legacy→each candidate→rollback target; compare all logical hashes, stable IDs, generations, receipts and exact/FTS oracle results. Test interrupted/resumed import and rollback after inserts, updates, hard deletes, namespace purge, and reinforcement. |
| Canonical atomicity | For both candidates, inject failure between every record/text/vector/edge/receipt write and commit: observe all old or all new state. No receipt for partial state. Validate database integrity plus application invariants after each reopen. |

Dependency order: immediate namespace/slot guards and compaction disablement → transactional compaction/ownership/phase repairs and strict restore → complete mutation receipts/effects/readiness → comparable canonical spike → fidelity/performance gates → opt-in migration → default switch only after rollback drill. Backup safety must not wait for backend selection.

- **A2:** consume generation-pinned views and the agreed readiness/unavailable policy, exact-search parity, same-namespace edges and no v2 associative tombstone relay. A1 stores all edge types without redesigning ranking.
- **A3:** implement the agreed timestamp/history/lifecycle fields and injected-clock migration rules before canonical schema freeze. A1 persists them atomically and preserves unknown legacy values; no implicit reinforcement from storage reads.
- **A4:** implement CONTRACTS receipt wire shape, namespace resolution, lineage retry tokens, structured errors and partial batches. Single-provider profile validation remains the default. Public readiness and force-option compatibility need release notes.
- **A5:** own timing/lock/rebuild/receipt-size instrumentation and comparison evidence. A1 supplies durable barriers and exact bytes; optimizing locks or batching cannot weaken them silently.
- **A6:** own synthetic crash/concurrency fixtures, deterministic episodes, trace schema/provenance and oracle integration. Episodes use side-effect-free reads unless explicitly testing feedback; no personal corpus or credentials.

## 9. Decisions and empirical release gates

Decided defaults: incremental containment first; metadata transaction selects text generation; canonical slot ownership with copy-on-write updates; serialize phase commit/publication and checkpointing; complete staged restore under stable ownership; lifetime retry receipts; one canonical database for either candidate; exact vectors retained; SQLite preferred only after measured gates; offline full reverse export for rollback after new writes.

Unresolved gates are concrete release blockers, not invitations to invent missing results:

CONTRACTS closes generation encoding, lifetime receipts/catalog batches, readiness, lifecycle schema/defaults and the two restore modes. Implement those interfaces without selecting alternatives.

1. **Recovery support gate:** verify fsync/rename/locking assumptions on declared local target filesystems, pinned backend APIs, and old-binary retirement. Network filesystems are unsupported initially. No automatic repair of ambiguous legacy compaction or historically damaged vectors.
2. **A5/A6 backend gate:** execute the specified real-engine comparison and crash/restore/rollback suites when authorized; publish evidence and confidence intervals. Neither performance superiority nor production recovery safety has been established here.

Future measurements may motivate a separately versioned comparison protocol. They cannot substitute for canonical fidelity or allow an acknowledged write to disappear silently.
