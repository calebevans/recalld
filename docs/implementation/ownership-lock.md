# Ownership release across an unrelated fork

The fix is based on PR15 `4bf07dc`. Stable sibling ownership first appeared in `3bffbfe`; the completed PR15 parent also contains backup/restore ownership callers and the corrected canonical-parent alias regression. No core45, schema, lifecycle, or retrieval ancestry is needed. The separate initial core45 reproduction is `d1026d2` on `study/ownership-lock-proof`.

## Deterministic mechanism

An unrelated `std::process::Command` runs on another thread and waits at a test-only pre-exec socket barrier. Only async-signal-safe syscalls execute in that child callback. While the child is stopped, the parent drops the actual owner and immediately reopens it. There are no timing sleeps or retries. Linux `/proc/<child>/fd` and `fdinfo` evidence identifies the matching device/inode, lock descriptor and owning parent PID; the descriptor has `FD_CLOEXEC=1`. Close-on-exec does not close a descriptor before exec.

On the minimal parent, stable-owner and legacy-directory probes both fail with `DatabaseLocked`, the vector probe fails with `FileLocked`, and the actual engine with a vector namespace fails with `DatabaseLocked`. The independent redb probe passes: its pinned Unix backend already explicitly unlocks in Drop. Baseline result: one passed, four failed, retained in `.validation/fork-before.log`. The captured stable-owner case has parent PID 578, child PID 585, FD 3, device 197 and inode 154205803; the child fdinfo reports `FLOCK ADVISORY WRITE 578` on that inode. The directory case has child PID 582 and inode 154205800. These are captured fixture identifiers, not portable expectations. This proves a mechanism producing the observed failure class. It does not identify the child holder from the original CI or earlier uninstrumented failures.

## Fix and ownership boundary

`OwnedFileLock` owns a freshly opened file and sets its acquired flag only after successful `FileExt::try_lock_exclusive`. Drop explicitly invokes the existing platform `FileExt::unlock` only for a successful acquisition in its acquiring process, then normal File drop closes the handle. Failed acquisitions never unlock another owner's description. Callers do not pass cloned or borrowed file descriptions. Inherited engines/files must not be used for writes after fork; this is the normal fork/exec contract, not support for using an inherited storage engine.

Stable sibling ownership, the legacy directory lock and vector-file locking share this guard. Field order is preserved: a vector mapping drops before its lock; engine metadata/vector/text/edge handles drop before directory and stable ownership. Error paths after acquisition get the same guard cleanup. No extra synchronization, retry, F_SETLK substitution, timeout, deletion of lock files or test serialization is introduced. Existing fs2 acquisition errors retain their mapping. Drop cannot return an unlock error: it logs failure and still closes the owned file, without adding a fallible sync or pretending durability was established. Platform lock/unlock support remains exactly fs2's; native runtime evidence here is Linux only.

Regression coverage includes actual Command pre-exec inheritance, independent redb/vector behavior, failed-acquisition destruction, live-owner exclusion in the same and another process, and canonical parent aliases. The expected-contender checks occur before parent release, and successful reacquisition occurs after it. The existing backup/restore ownership checks also pass in focused validation.

Later schema branches add `OfflineSnapshot::_source_lock` with an explicit File type. Its merge must retain the guard type (`crate::storage::ownership::OwnedFileLock`) at the same field position; inferred local callers need no change. This single integration adjustment must be checked with those branches and does not justify schema/core ancestry in PR15's fix.
