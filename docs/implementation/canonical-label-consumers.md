# Canonical structured-label read consumers

This slice carries persisted `StructuredLabels` through cached records, pipeline get/search/similar results, HTTP hydration, and MCP get/search/similar/list/neighbor results. A canonical label object is authoritative even when all lists are empty. Only records without that object use the existing legacy tag parser and its display conventions.

Existing `entities`, `topics`, and `emotions` response arrays keep their types and legacy behavior. An optional `labels` object carries all three exact arrays plus persisted provenance, and is omitted when there is no canonical object. Compact MCP recall includes this object only for canonical results. `LegacyRetainedOnly` remains retained-only; no label spelling, ordering, duplicates, or provenance is reconstructed from an entity index. Cache weight includes the added label allocations.

Structured hard filters remain separate from explicit raw-tag filters. The shared pipeline validates them against the resolved namespace before provider/channel work and applies them during canonical eligibility before vector, FTS, entity, and metadata caps. Listing applies the same predicate before totals and offset/limit. Caller labels are compiled once after validation while their original strings remain on the internal query. Matching uses whole-label Unicode lowercase equality, without entity aliases, trimming, or Unicode normalization. Canonical stored values are folded during comparison; their remaining cost is a measurement item, not a new index/cache. Legacy filters retain strict tag encoding/rejection. Canonical filters accept UTF-8 within the persisted label byte/count limits. Explicit raw-tag filters retain their existing semantics.

## Fixture provenance and limits

The Unicode offline fixture first uses the real legacy store and schema migration to obtain valid vector references, lifecycle fields, namespace bindings, and a gated canonical layout. With the snapshot closed, test code writes explicitly authored label payloads directly to isolated redb records. It then reopens `OfflineSnapshot` through its normal structural canonical validation, which does not authenticate the authored label payload or prove publication. This direct fixture edit has no native insertion/publication receipt and does not demonstrate a supported native write. Both `NativeV2` and `LegacyRetainedOnly` values in the authored test data exercise exact reader copying; neither is evidence that migration recovered missing labels or established native provenance.

The HTTP/MCP tests use real routing/dispatch and hydration against that offline fixture, with separate isolated legacy placeholder subsystems. They do not open a native ordinary-serving engine. The list test inserts synthetic schema-bearing codec rows into an already-open legacy-control test database solely to exercise reader predicate/total/pagination ordering; it is not a valid native store or a startup/publication proof. No format guard, ordinary startup gate, or negative native/legacy admission test is removed or relaxed. A valid native insertion → publication → transport read → reopen proof belongs to a future join with Pascal’s actual native writer, including exact provenance and rejection of malformed profile/vector proof.
