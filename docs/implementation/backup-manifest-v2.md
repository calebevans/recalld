# Canonical BackupManifestV2

Schema-v2 `run_backup` now emits `backupFormatVersion: 2` and `canonicalSchemaVersion: 2`. Each required canonical file carries its exact length, legacy CRC32 and SHA-256 (32 byte JSON array). The `snapshot` description includes the existing backend, complete typed control and immutable migration evidence, credential-free namespace configuration/profile/provenance/policy, selected text descriptor, validated restore ancestry when present, counts of records/tombstones/vectors/edges/retained receipts, counts by namespace/phase and edge type, and explicit derived-artifact rebuild requirements. No provider calls or serving activation occur.

Manifest generation requires complete canonical validation and exactly the metadata-derived file inventory under the backup caller's ownership. It never treats a supplied file list as proof of completeness. Metadata and edges inspection uses disposable copies; source bytes remain unchanged. Archive publication still uses the existing synced temporary-file publication path. Physical backup files can contain unreachable forgotten bytes; retained-only logical export is the separate `logical_export` path. Neither is a forensic-erasure claim.

`backup::schema_manifest::validate_manifest_snapshot(stage, manifest)` is called from actual restore extraction after canonical inventory validation and before any deletion reconciliation or lineage fork. It checks versions, lengths/SHA, exact canonical inventory and all declared snapshot metadata/counts against fresh validated inspection. It validates the original archive lineage, not the newly forked lineage. Pascal's separate `ad64089` bridge supplies production fork/ancestry semantics, retains historical receipt/key and migration evidence, and consumes validated applied effects after staging rebuild. Integrators must preserve this pre-fork call position and shared effects/ledger/lineage validators.

Unknown or partial required versions fail closed. Manifest input and output are limited to 16 MiB; restore checks advertised size and bounds decompressed reads independently. Legacy manifests without a format field remain format 1 and require the same complete semantic validation plus the existing extraction CRC checks. Removing V2 descriptors does not permit missing or corrupt canonical files to pass as V1. Checksums detect damage and fidelity errors, not authenticity.

Tests exercise real `run_backup` and restore extraction, exact identity/configuration/counts, source byte immutability, checksum-consistent lies about counts/generation/profile/text/readiness, incorrect SHA, omitted namespace files, future/partial versions, oversized manifest rejection, legacy CRC compatibility and the existing corruption/path/ownership suite. Production restore forks, real integrated ledger/effects fixtures, provider-dependent index readiness and filesystem power-loss/I/O fault coverage remain separately owned integration requirements; standalone copy-restore tests do not claim those semantics.

Completed logical imports retain a derived `logical_import_progress` checkpoint so retrying the original import can verify identity. Restore recognizes that table after full canonical snapshot validation, then deletes it only inside the private lineage-fork transaction. It is never used to admit a snapshot or bypass the importing marker. The original imported source/checkpoint stays byte-identical and retryable; the restored lineage has no inherited import destination identity. A real schema migration → export/import → V2 backup → historical restore regression failed before this correction and passes afterward.
